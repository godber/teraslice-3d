Chapter 08 · SwiftUI on visionOS

SwiftUI spatial UI

Four views: the RealityView host, the floating control ornament, a jobs list, and a settings form. Everything here is ordinary SwiftUI — the platform-specific parts are RealityView, .ornament, and the fact that glass materials and hover effects come for free.

PipelineVolumeView — the SwiftUI ⇄ RealityKit bridge

Sources/Views/PipelineVolumeView.swiftlines 7–29
public struct PipelineVolumeView: View {
    @Environment(AppState.self) private var appState

    @State private var graphEntity = PipelineGraphEntity()
    @State private var rotation: Rotation3D = .identity

    public var body: some View {
        #if os(visionOS)
        RealityView { content in
            content.add(graphEntity)
            graphEntity.updateGraph(appState.graphData)
        } update: { content in
            // Graph entity automatically updates child transforms
        }
        .onChange(of: appState.graphData) { _, newGraphData in
            graphEntity.updateGraph(newGraphData)
        }
        .ornament(attachmentAnchor: .scene(.bottom)) {
            ControlOrnamentView()
                .environment(appState)
        }
        #else
        …2D fallback…
        #endif
    }
}

RealityView's two closures

  • make: runs once, when the view first appears. It receives a RealityViewContent — the handle to the scene's root — and this is where you add your entity hierarchy. It can be async if you need to load assets.
  • update: runs whenever SwiftUI state that the view reads changes, and is meant for pushing state into the scene. Here it's empty, with the reasoning in a comment: because graphEntity is a long-lived object mutated directly, nothing needs to happen in update.
  • .onChange(of:) is doing the real work instead — it fires when appState.graphData becomes a different value (hence PipelineGraph: Equatable) and rebuilds the geometry. Functionally equivalent to doing the same test in update:, and arguably clearer about which state matters.
🟠
Swift note · @State holding a class instance

@State private var graphEntity = PipelineGraphEntity() stores a reference type in view state. This is the standard way to keep a RealityKit entity alive across body re-evaluations — PipelineVolumeView is a struct that gets recreated constantly, but the entity behind it persists. (@State initialises its value once, on first appearance, and later re-inits of the struct don't reset it.)

🔴
Gap · no gestures, so the interaction components do nothing

NodeEntity and LinkEntity both carry InputTargetComponent and a collider, but nothing attaches a gesture to the RealityView. On visionOS, entity taps arrive through SwiftUI: 

.gesture(
    SpatialTapGesture()
        .targetedToAnyEntity()
        .onEnded { value in
            if let node = value.entity as? NodeEntity { appState.selectedNodeID = node.nodeID }
        }
)

.targetedToAnyEntity() is the key modifier — it turns a 2D gesture into one that reports which entity was hit, via EntityTargetValue. Add that and selectedNodeID stops being dead state. DragGesture and RotateGesture3D work the same way for direct manipulation — which is also what the unused @State private var rotation: Rotation3D (and the import Spatial above it) was clearly staged for.

The non-visionOS fallback

The #else branch renders a plain SwiftUI summary — an SF Symbol, the server name and version, and two .thinMaterial cards listing the first five nodes and links. It exists so swift build works on macOS, and it doubles as a quick way to sanity-check the data layer without booting the simulator. Note it's the only place appState.start() is called, from .task { }.

Ornaments: UI that floats outside the window

An ornament is a visionOS-specific presentation: a small view anchored to the edge of a window or volume, floating slightly in front of it in depth. Toolbars, tab bars and media controls on visionOS are all ornaments. .scene(.bottom) anchors this one below the volume — you can see it in the annotated spatial UI screenshot.

The SwiftUI idioms in that block

IdiomWhat it does
HStack { … } / VStack / Divider()Layout primitives. spacing: and .padding are how visionOS UI gets its generous touch targets.
Menu { } label: { }A pull-down menu; two trailing closures for content and label.
Label(_:systemImage:) + Image(systemName:)SF Symbols — server.rack, magnifyingglass, arrow.clockwise, gear, cpu, trash, cube.transparent.fill. Vector, weight-matched to text, and free.
ForEach(appState.serverList)No id: needed because ServerConfig is Identifiable.
.background(.ultraThinMaterial, in: Capsule())System glass, clipped to a shape. .ultraThin → .regular → .thick trade legibility against seeing your room through it. This is the visionOS look, and you get it by not hand-rolling colours.
.pickerStyle(.segmented), .buttonStyle(.bordered), .textFieldStyle(.plain)Style modifiers — the same control adapts per platform.
.rotationEffect + .animation(_:value:)The spinning refresh icon: a repeating linear animation driven by isRefreshing.
.sheet(isPresented: $showSettings)Modal presentation bound to a @State Bool. $ makes the two-way binding.
Task { await appState.refreshData() }Button actions are synchronous, so async work is wrapped in a Task. Extremely common pattern.
🎛️
Two rough edges in this view

@State private var showInspector = false is declared and never used — JobsInspectorView has no way to be presented, despite being fully written. And .help("Refresh Pipeline Data") is a hover-tooltip affordance inherited from macOS; on visionOS, prefer .accessibilityLabel plus a visible label for anything a user needs to understand, since an icon-only button in a glass capsule is not self-explanatory.

🪟
Sheets presented from a volume

Both SettingsView and (eventually) the jobs inspector are presented as .sheets from a view inside an ornament attached to a volume. That nesting is worth testing early on device — modal presentation semantics differ between windows and volumes, and for a settings panel of this size a separate WindowGroup opened with openWindow(id:) is often the better spatial design: it can be placed wherever the user wants and stays visible next to the graph, instead of covering it.

JobsInspectorView — lists, navigation, toolbars

NavigationStack {
    List {
        Section("Jobs (\(appState.jobs.count))") {
            ForEach(appState.jobs) { job in
                VStack(alignment: .leading, spacing: 4) {
                    HStack {
                        Text(job.name).font(.headline)
                        Spacer()
                        Text(job.status.rawValue.capitalized)
                            .font(.caption)
                            .padding(.horizontal, 8).padding(.vertical, 3)
                            .background(statusColor(job.status).opacity(0.2), in: Capsule())
                            .foregroundStyle(statusColor(job.status))
                    }
                    HStack {
                        Label("\(job.workers) Workers", systemImage: "cpu")
                        Spacer()
                        Text("ID: \(job.job_id.prefix(8))...")
                            .font(.caption2).monospaced().foregroundStyle(.secondary)
                    }
                    .font(.caption).foregroundStyle(.secondary)
                }
            }
        }
    }
    .navigationTitle("Jobs & Connectors")
    .toolbar {
        ToolbarItem(placement: .confirmationAction) {
            Button("Done") { dismiss() }
        }
    }
}
.frame(minWidth: 500, minHeight: 600)

Worth noting:

  • NavigationStack provides the title and toolbar; it's the current API (NavigationView is deprecated).
  • Spacer() inside an HStack pushes its neighbours apart — the standard way to right-align.
  • Semantic fonts and colours — .headline, .caption, .secondary — adapt to the user's text size and to visionOS's own contrast rules. Prefer them to hard-coded sizes.
  • .toolbar { ToolbarItem(placement: .confirmationAction) } + @Environment(\.dismiss) — the standard "Done" affordance for a modal. dismiss is a callable value: dismiss().
  • statusColor(_:) is a private helper duplicating the switch already present in JobStatus.statusColorName and in LinkEntity.material(for:) — three copies of one mapping. A single var color: Color on JobStatus would be the fix, and would keep the volume's pipe colours and the list's badges guaranteed in sync.

SettingsView — forms and destructive actions

Sources/Views/SettingsView.swiftlines 14–63 (condensed)
Form {
    Section("Backend Servers") { … }

    Section("Add Custom Server") {
        TextField("Server Name (e.g. Production Cluster)", text: $newServerName)
        TextField("Base URL (e.g. http://192.168.1.50:8000)", text: $newServerURL)
        Button("Add Server") {
            guard !newServerName.isEmpty, !newServerURL.isEmpty else { return }
            let newConfig = ServerConfig(name: newServerName, baseURLString: newServerURL, isMock: false)
            appState.serverList.append(newConfig)
            appState.switchServer(newConfig)
            newServerName = ""
            newServerURL = ""
        }
        .disabled(newServerName.isEmpty || newServerURL.isEmpty)
    }

    Section("Cache Controls") {
        Button(role: .destructive, action: {
            Task {
                let success = await appState.clearServerCache()
                cacheClearedMessage = success ? "Cache cleared successfully!" : "Failed to clear cache."
            }
        }) {
            Label("Clear Teraslice Backend Cache", systemImage: "trash")
        }

        if let msg = cacheClearedMessage { Text(msg).font(.caption).foregroundStyle(.secondary) }
    }
}
  • Form + Section — grouped settings layout, styled per platform.
  • $newServerName — the projected value of a @State, i.e. a Binding<String>. Compare with Bindable(appState).searchText in the ornament: same concept, different source of truth.
  • Button(role: .destructive) — semantic role; the system renders it in red. Note there's no confirmation step before clearing a shared backend cache; a .confirmationDialog would be appropriate.
  • .disabled(…) — declarative enablement, derived from state rather than toggled imperatively.
  • The guard … else { return } inside the button duplicates the .disabled condition. Harmless belt-and-braces.
  • No validation of the URL — a typo produces a ServerConfig whose baseURL is nil, which fails silently into mock data (chapter 05). And nothing is persisted across launches.
