Chapter 07 · RealityKit

RealityKit entities

Three files, 303 lines, and the whole 3D rendering layer. This is where you learn RealityKit's entity-component model, mesh and material generation, collision and hover, and the quaternion maths needed to point a cylinder at something.

Entity ModelComponent MeshResource SimpleMaterial CollisionComponent InputTargetComponent HoverEffectComponent simd_quatf

RealityKit's mental model

RealityKit is an entity-component-system (ECS) renderer. Three nouns:

  • Entity — a node in the scene graph. It has a transform, a parent, children, and a bag of components. By itself it draws nothing.
  • Component — a struct of data attached to an entity that gives it a capability: ModelComponent makes it visible, CollisionComponent makes it hit-testable, InputTargetComponent makes it interactive. You attach them with entity.components.set(…).
  • System — code that runs every frame over all entities holding a given set of components. This app defines none; chapter 10 explains why it probably should.

If you know SceneKit or Three.js, the shift is that behaviour lives in components and systems rather than in subclass overrides. Coordinates are right-handed, Y-up, metres, and each entity's transform is relative to its parent.

NodeEntity: a sphere per connector

Sources/RealityKit/NodeEntity.swiftlines 12–49
public final class NodeEntity: Entity, HasModel, HasCollision {
    public let nodeID: String
    public let connectorType: ConnectorType
    public private(set) var radius: Float

    @MainActor
    public init(node: GraphNode, position: SIMD3<Float> = .zero, radius: Float = 0.04) {
        self.nodeID = node.id
        self.connectorType = node.connectorType
        self.radius = radius
        super.init()

        updateMeshAndCollision(radius: radius, isIncoming: node.isIncoming)
        self.position = position
    }

    @MainActor
    public required init() { … }        // required by Entity

    @MainActor
    public func updateMeshAndCollision(radius: Float, isIncoming: Bool) {
        self.radius = radius
        let mesh = MeshResource.generateSphere(radius: radius)
        let material = NodeEntity.material(for: self.connectorType, isIncoming: isIncoming)

        self.model = ModelComponent(mesh: mesh, materials: [material])

        // Enable spatial interaction (gaze + pinch hover)
        let shape = ShapeResource.generateSphere(radius: radius * 1.2)
        self.components.set(CollisionComponent(shapes: [shape]))
        self.components.set(InputTargetComponent())
        self.components.set(HoverEffectComponent())
    }
}

What each line buys you

APIRole
MeshResource.generateSphere(radius:) Procedural geometry — no asset file needed. MeshResource also has generateBox, generatePlane, generateCylinder, generateCone, and generateText.
SimpleMaterial(color:isMetallic:) The quick PBR-ish material: base colour, roughness, metallic. Takes a platform colour (UIColor on visionOS), hence the typealias dance from chapter 01.
ModelComponent(mesh:materials:) The component that actually renders. materials is an array because a mesh can have multiple parts.
ShapeResource.generateSphere(radius:) A collision shape — separate from the render mesh, and deliberately 20% larger here so gaze targeting is forgiving.
CollisionComponent Makes the entity hit-testable. Required for input: without it, gaze and taps pass straight through.
InputTargetComponent Declares "this entity can receive input". Pairs with a SwiftUI gesture attached to the RealityView.
HoverEffectComponent The system highlight when you look at the entity. Rendered outside your process for privacy — your app never learns where the user is looking, which is a core visionOS design constraint.
👁
Why gaze data never reaches your code

HoverEffectComponent exists because the compositor can highlight what you're looking at without telling the app. An app only learns about a target when the user commits — a pinch, which arrives as a tap gesture. Designing around that (generous colliders, system hover effects, no "on hover, fetch details") is the platform idiom, not a limitation to work around. visionOS 2 added custom hover effects if the default highlight isn't enough.

🟠
Swift note · HasModel, HasCollision, and required init()

HasModel and HasCollision are convenience protocols from RealityKit's first generation. Conforming gives you the self.model = … and self.collision = … shorthand instead of components.set(ModelComponent(…)). Both spellings appear in this one method — self.model for the model, components.set for everything else. The modern, uniformly-applicable idiom is components.set; if you're reading Apple sample code from 2023 onward you'll rarely see Has*.

public required init() is inherited from Entity: RealityKit needs to be able to construct entities generically (e.g. when loading a scene), so every subclass must provide a no-argument initialiser. Note it fabricates dummy values (nodeID = "unknown") — a sign that let properties plus a required init are a slightly awkward fit, and part of why component-based design is preferred: a NodeIDComponent would avoid subclassing altogether.

Colour mapping

Sources/RealityKit/NodeEntity.swiftlines 51–72 (condensed)
public static func material(for connectorType: ConnectorType, isIncoming: Bool) -> SimpleMaterial {
    let color: NodePlatformColor
    switch connectorType {
    case .kafkaIncoming: color = .systemYellow
    case .kafkaOther:    color = isIncoming ? .systemYellow : .systemBlue
    case .elasticsearch: color = .systemGreen
    case .dataGenerator: color = .systemPurple
    case .noop, .unknown: color = .systemGray
    }

    var mat = SimpleMaterial(color: color, isMetallic: false)
    mat.roughness = 0.3
    return mat
}

Same palette as the web frontend (yellow = incoming Kafka, blue = internal Kafka, green = Elasticsearch), using system colours so they stay consistent with platform UI. roughness = 0.3 gives a slight sheen; isMetallic: false keeps the colour readable rather than mirror-like — which matters in passthrough, where a metallic sphere reflects an environment map that has nothing to do with your actual room.

LinkEntity: pointing a cylinder at a target

Nodes are easy — a sphere has no orientation. Links are the interesting geometry problem: given two endpoints, produce a cylinder that spans them.

Sources/RealityKit/LinkEntity.swiftlines 43–87 (condensed)
let delta = targetPos - sourcePos
let distance = simd_length(delta)
guard distance > 0.001, !distance.isNaN else { return }

// Worker scale matching web frontend: ((workers - 1) / (200 - 1)) * (20 - 1) + 1
let workersClamped = Float(max(1, min(200, link.workers)))
let workerScale = ((workersClamped - 1.0) / 199.0) * 19.0 + 1.0
let basePipeRadius: Float = 0.005
let rawRadius = basePipeRadius * workerScale * scale
let radius = simd_clamp(rawRadius, 0.002, 0.015)

let mesh = MeshResource.generateCylinder(height: distance, radius: radius)
self.model = ModelComponent(mesh: mesh, materials: [LinkEntity.material(for: link.status)])

// Position at midpoint between source and target
self.position = (sourcePos + targetPos) * 0.5

// Orient cylinder (default Y-axis) along vector delta with NaN safeguards
let direction = simd_normalize(delta)
let defaultUp = SIMD3<Float>(0, 1, 0)
let dot = simd_clamp(simd_dot(defaultUp, direction), -1.0, 1.0)

if dot > 0.9999 {
    self.orientation = simd_quatf(angle: 0, axis: SIMD3<Float>(1, 0, 0))       // already aligned
} else if dot < -0.9999 {
    self.orientation = simd_quatf(angle: .pi, axis: SIMD3<Float>(1, 0, 0))     // antiparallel: flip
} else {
    let axis = simd_cross(defaultUp, direction)
    let axisLen = simd_length(axis)
    if axisLen > 0.0001 {
        self.orientation = simd_quatf(angle: acos(dot), axis: axis / axisLen)
    } else { … }
}

let shape = ShapeResource.generateBox(size: SIMD3<Float>(radius * 3, max(0.01, distance), radius * 3))
self.components.set(CollisionComponent(shapes: [shape]))

The rotation, unpacked

generateCylinder produces a cylinder centred at the origin, extending along +Y. To make it span two points you need to (a) move it to the midpoint and (b) rotate +Y onto the direction vector. That rotation is the standard "align one vector to another":

  • Axis = cross(up, direction) — perpendicular to both, so rotating about it sweeps one onto the other.
  • Angle = acos(dot(up, direction)) — for unit vectors, the dot product is the cosine of the angle between them.
  • Both degenerate cases must be special-cased: if the vectors are parallel the cross product is zero (no axis exists, and none is needed); if antiparallel, any perpendicular axis works, so the code picks X and rotates π.
  • simd_clamp(dot, -1, 1) before acos — floating-point error can push a dot product to 1.0000001, and acos of that is NaN. A single NaN in a transform makes the entity vanish and is miserable to debug, which is why this file is so defensive about it.
🟠
Swift note · quaternions in 30 seconds

simd_quatf represents a rotation as an axis plus an angle, stored as four floats. Compared with Euler angles they compose cleanly (q1 * q2), interpolate smoothly (simd_slerp), and never hit gimbal lock. RealityKit's Transform is exactly (scale: SIMD3, rotation: simd_quatf, translation: SIMD3), and entity.orientation / entity.position / entity.scale are conveniences onto it. You rarely construct a quaternion by hand except in cases like this one.

Thickness by worker count

The formula is lifted verbatim from the web frontend — workers 1…200 map linearly to a scale of 1…20 — then multiplied by the volumetric scale factor and clamped to 2 mm…15 mm. The clamp is what keeps a 200-worker job from becoming a fat sausage in a small volume, and testAdaptiveGeometryScaling pins both ends of the range. Status drives colour through the same JobStatus switch as the rest of the app: green running, blue starting, orange stopped/stopping, red failing/failed, purple completed, grey unknown.

📦
Why the collider is a box

ShapeResource has no cylinder primitive, so the link's collider is a box radius*3 wide and distance tall — generously wide on purpose, since a 2 mm pipe is nearly impossible to gaze-target precisely. The box inherits the entity's rotation, so it stays aligned with the pipe.

PipelineGraphEntity: the scene manager

Sources/RealityKit/PipelineGraphEntity.swiftlines 40–90 (condensed)
public final class PipelineGraphEntity: Entity {
    public private(set) var nodeEntities: [String: NodeEntity] = [:]
    public private(set) var linkEntities: [String: LinkEntity] = [:]
    public private(set) var simulation = ForceSimulation3D()

    @MainActor
    public func updateGraph(_ graph: PipelineGraph) {
        simulation.setup(graph: graph)
        simulation.runSimulation(iterations: 120)

        for (_, entity) in nodeEntities { entity.removeFromParent() }
        for (_, entity) in linkEntities { entity.removeFromParent() }
        nodeEntities.removeAll()
        linkEntities.removeAll()

        let projection = VolumetricProjection(nodes: Array(simulation.nodes.values),
                                              targetVolumeSpan: 0.40)

        for node in graph.nodes {
            let simPos = simulation.nodes[node.id]?.position ?? .zero
            let renderedPos = projection.project(simPos)
            let radius = computeNodeRadius(for: node, projection: projection,
                                           totalNodeCount: graph.nodes.count)
            let nodeEntity = NodeEntity(node: node, position: renderedPos, radius: radius)
            self.addChild(nodeEntity)
            nodeEntities[node.id] = nodeEntity
        }

        for link in graph.links {
            guard let simSourcePos = simulation.nodes[link.source]?.position,
                  let simTargetPos = simulation.nodes[link.target]?.position else { continue }
            let linkEntity = LinkEntity(link: link,
                                        sourcePos: projection.project(simSourcePos),
                                        targetPos: projection.project(simTargetPos),
                                        scale: projection.scale)
            self.addChild(linkEntity)
            linkEntities[link.id] = linkEntity
        }
    }
}

Points of interest:

  • Dictionaries keyed by domain id — the bridge between "graph data" and "scene graph". Any future selection, filtering or animation code looks up entities here rather than walking children.
  • removeFromParent() detaches an entity from the scene; dropping the last reference then deallocates it. The rebuild is wholesale: every refresh throws away all geometry and makes it again.
  • Links skip missing endpoints via guard … else { continue }, so a malformed graph degrades to fewer pipes instead of crashing.
  • Density-aware node sizing:
Sources/RealityKit/PipelineGraphEntity.swiftlines 51–56
private func computeNodeRadius(for node: GraphNode, projection: VolumetricProjection,
                               totalNodeCount: Int) -> Float {
    let densityFactor = 1.0 / sqrt(max(Float(totalNodeCount) / 10.0, 1.0))
    let baseRadius: Float = node.isIncoming ? 0.18 : 0.12
    return simd_clamp(baseRadius * projection.scale * densityFactor, 0.008, 0.035)
}

Three effects multiplied together: incoming Kafka topics are 50% bigger (they're the entry points you look for first), the projection scale keeps apparent size stable as the graph grows, and the inverse-square-root density factor shrinks nodes further in crowded graphs. Clamped to 8 mm…35 mm so they never vanish or dominate.

🔴
Gap · stepSimulation() is never called

The class has a per-frame update method — tick the simulation with alpha: 0.1, re-project, move node entities, rebuild link transforms — and nothing in the app invokes it. The graph is therefore static: it snaps to its solved layout on each refresh with no visible settling motion, which is a large part of the charm of a force-directed graph.

To animate it you need a frame loop. Two idiomatic options: subscribe to SceneEvents.Update from inside the RealityView's make: closure, or write a proper RealityKit System, which is the ECS-native answer and gets you scheduling for free.

🔴
Gap · full teardown and mesh regeneration on every poll

Every 30 seconds, all entities are destroyed and all meshes regenerated — even when the topology is unchanged, which is the common case. MeshResource.generateSphere/generateCylinder build vertex buffers on the main thread, so this is both a hitch and a lost opportunity: with entities kept alive you could animate positions and cross-fade status colours instead of snapping.

Two concrete improvements: (1) diff the incoming graph against nodeEntities/linkEntities and only add/remove what changed — the simulation already reconciles positions this way; (2) generate one unit-height cylinder mesh and one unit sphere, then express per-link size purely as entity.scale, so resizing a pipe becomes a transform update rather than new geometry. Shared MeshResources also let the renderer batch draws.
