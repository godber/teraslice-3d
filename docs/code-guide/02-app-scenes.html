Chapter 02 · SwiftUI app structure

App, scenes & volumes

34 lines of Teraslice3DApp.swift decide what kind of thing this app is on visionOS — a flat panel, a box of space on your desk, or a room. Plus the Xcode build settings that quietly matter as much as the Swift does.

SwiftUI · App Scene WindowGroup .volumetric Info.plist scene roles xros SDK

The entry point

Sources/App/Teraslice3DApp.swiftlines 1–31
import SwiftUI

@main
struct Teraslice3DApp: App {
    @State private var appState = AppState()

    var body: some Scene {
        #if os(visionOS)
        // 1. Primary Application Window
        WindowGroup {
            PipelineVolumeView()
                .environment(appState)
        }
        .defaultSize(width: 800, height: 600)

        // 2. 3D Volumetric Window
        WindowGroup(id: "volumetric-main") {
            PipelineVolumeView()
                .environment(appState)
        }
        .windowStyle(.volumetric)
        .defaultSize(width: 1.0, height: 1.0, depth: 1.0, in: .meters)
        #else
        WindowGroup {
            PipelineVolumeView()
                .environment(appState)
        }
        .defaultSize(width: 800, height: 600)
        #endif
    }
}

There is no main.swift, no UIApplicationMain, no app delegate. The pieces:

  • @main + App — the protocol supplies a default main(), so this struct is the executable's entry point. Exactly one type per target may be @main.
  • var body: some Scene — an app's body is made of Scenes, not views. A scene is a unit the system manages: it can be opened, closed, moved, and on visionOS placed anywhere in your room. Views live inside scenes.
  • Two scenes, listed like views. The scene builder collects both WindowGroups; declaring them does not open them. visionOS opens the app's default scene at launch, and the app can open others later by id.
  • @State private var appState = AppState() — created once for the life of the app and passed down with .environment(appState). Chapter 03.

The three presentation styles on visionOS

This is the platform's central design idea, and it maps directly onto SwiftUI scene types. Apple's HIG treats them as a progression from "shares space politely" to "takes over the room".

StyleDeclared asShapeIn this app
Window WindowGroup (default style) Flat glass panel, sized in points, with a system chrome bar and resize handles Scene 1 — the fallback / control panel
Volume WindowGroup + .windowStyle(.volumetric) Bounded box measured in metres; content can extend in all three axes and be viewed from any side Scene 2 — where the graph lives
Immersive space ImmersiveSpace Unbounded; content anywhere in the room, passthrough dimmed or replaced Not implemented — see chapter 10
📐
Points vs metres

.defaultSize(width: 800, height: 600) is in points; the volumetric variant uses .defaultSize(width:height:depth:in: .meters). The unit argument comes from the Spatial framework's UnitLength. A 1 m³ volume is roughly a big cardboard box on your desk — and the graph inside it is deliberately scaled to 0.40 m so it never touches the walls (chapter 06).

What a volume gives you, and what it doesn't

  • Does: real stereo depth, motion parallax as you lean, the ability to walk around the box and see the graph from behind. A baseplate and drag bar are drawn by the system.
  • Doesn't: give you a camera. There is no view matrix to animate — you are the camera. Zooming means scaling your content or resizing the volume, and "orbiting" means rotating the content or walking around it. This is why the web frontend's orbit controls have no direct equivalent here.
  • Doesn't: let content spill outside the declared box. Geometry beyond the bounds is clipped, which is the whole reason VolumetricProjection exists.

Which scene actually opens?

Reading the Swift alone, you'd expect the plain WindowGroup to open first — it's listed first. But the screenshot in the spatial UI guide clearly shows a volume. The missing half of the answer is in the Xcode project:

Teraslice3D.xcodeproj/project.pbxprojbuild settings, both configurations
SDKROOT = xros;
SUPPORTED_PLATFORMS = "xros xrsimulator";
XROS_DEPLOYMENT_TARGET = 2.0;
TARGETED_DEVICE_FAMILY = 7;
SWIFT_VERSION = 6.0;
PRODUCT_BUNDLE_IDENTIFIER = com.teraslice.Teraslice3D;

GENERATE_INFOPLIST_FILE = YES;
GENERATE_INFOPLIST_KEY_UIApplicationSceneManifest_Generation = YES;
GENERATE_INFOPLIST_KEY_UIApplicationPreferredDefaultSceneSessionRole = UISceneSessionRoleVolumetricApplication;
GENERATE_INFOPLIST_KEY_NSAppTransportSecurity_NSAllowsArbitraryLoads = YES;
SettingMeaning
SDKROOT = xrosBuild against the visionOS SDK. xrsimulator is the simulator slice; xros is device.
XROS_DEPLOYMENT_TARGET = 2.0Minimum visionOS. Anything introduced in visionOS 2 is available unconditionally; visionOS 1 devices can't install it.
TARGETED_DEVICE_FAMILY = 7Device family 7 = Apple Vision. (1 = iPhone, 2 = iPad, 6 = Mac.)
SWIFT_VERSION = 6.0Swift 6 language mode → strict concurrency checking. This is why Sendable shows up everywhere. ch. 03
…PreferredDefaultSceneSessionRole = UISceneSessionRoleVolumetricApplicationTells the system the app's preferred launch scene role is volumetric, so launching lands you in a volume rather than a flat window.
…NSAllowsArbitraryLoads = YESDisables App Transport Security so plain http://127.0.0.1:8000 works. ch. 05
GENERATE_INFOPLIST_FILE = YESThere is no checked-in Info.plist; Xcode synthesises one from these GENERATE_INFOPLIST_KEY_* settings at build time.
🔴
Gap · the second scene is unreachable from the UI

WindowGroup(id: "volumetric-main") can only be opened programmatically, via openWindow(id:). ControlOrnamentView declares @Environment(\.openWindow) private var openWindow — and never calls it. So the explicit volume is dead code today; the volume you see at launch comes from the scene-role plist key applied to the app's default scene. If you want the two-scene design from AVP-SPEC.md (flat control panel plus a separate volume), wiring that button is the smallest possible next step.

🧩
Both scenes show the same view

Scene 1 and scene 2 both host PipelineVolumeView(). Inside that view, the #if os(visionOS) branch always renders a RealityView — it does not know or care which scene it's in. A more finished app would host distinct views per scene (2D dashboard vs. 3D graph), and can detect its context with the \.supportsMultipleWindows / scene-specific environment values, or simply by being given different root views at declaration time.

Two build systems, one source tree

The directory contains both an Xcode project and a Swift package manifest, describing the same Sources/ folder:

Package.swiftlines 1–30
// swift-tools-version: 6.0
import PackageDescription

let package = Package(
    name: "Teraslice3D",
    platforms: [
        .visionOS(.v2),
        .macOS(.v15)
    ],
    products: [
        .executable(name: "Teraslice3D", targets: ["Teraslice3D"]),
    ],
    targets: [
        .executableTarget(name: "Teraslice3D", dependencies: [], path: "Sources"),
        .testTarget(name: "Teraslice3DTests", dependencies: ["Teraslice3D"], path: "Tests")
    ]
)

The package exists so swift build and swift test work from the command line on a Mac — which is why the #else branch of PipelineVolumeView exists at all, and why NodeEntity aliases NSColor. The visionOS app itself is built from Teraslice3D.xcodeproj. Zero external dependencies: dependencies: [].
