Chapter 03 · Observation & Swift concurrency

State & concurrency

AppState is 109 lines and touches nearly every modern Swift feature at once: the @Observable macro, the SwiftUI environment, actors, Tasks, cancellation, and the Swift 6 data-race rules. It also contains this app's most instructive rough edges.

Observation @Observable @State / @Environment Task @MainActor Sendable Bindable

The @Observable model

Sources/App/AppState.swiftlines 12–33
@Observable
public final class AppState: @unchecked Sendable {
    public var activeServer: ServerConfig = .defaultLocal
    public var serverList: [ServerConfig] = [.defaultLocal, .mockDataServer]

    public var graphData: PipelineGraph = MockGraphProvider.samplePipelineGraph()
    public var jobs: [JobDetails] = MockGraphProvider.sampleJobDetails()
    public var serverVersion: String = "Connecting..."

    public var selectedNodeID: String? = nil
    public var selectedLinkID: String? = nil

    public var searchText: String = ""
    public var filterMode: FilterMode = .highlight

    public var isAutoRefreshEnabled: Bool = true
    public var autoRefreshInterval: TimeInterval = 30.0
    public var isRefreshing: Bool = false
    public var lastRefreshedAt: Date? = nil

    private let apiClient = TerasliceAPIClient()
    private var refreshTask: Task<Void, Never>? = nil
}

@Observable is a macro from the Observation framework (Swift 5.9 / iOS 17 / visionOS 1 and later). At compile time it rewrites every stored property into a computed property that reports reads and writes to an ObservationRegistrar. The consequences:

  • No @Published, no ObservableObject, no objectWillChange. Plain vars are enough. If you read older SwiftUI tutorials you'll see the Combine-based pattern; this is its replacement.
  • Tracking is per-property and per-view. A view that reads only appState.isRefreshing is not invalidated when graphData changes. With the old ObservableObject, any published change redrew every observer. That granularity matters here: rebuilding the RealityKit scene is expensive.
  • Tracking follows actual reads. SwiftUI records which properties a body touched during evaluation, so a property read inside an if branch that didn't run is not tracked.
🟠
Swift note · final class

final forbids subclassing, which lets the compiler use direct dispatch instead of a vtable lookup. Default to final on classes you don't intend to subclass — it is both faster and clearer.

Getting the model into views

Three property wrappers, three different jobs. Getting these straight is most of learning SwiftUI data flow:

WrapperMeansIn this app
@State This view owns the value; it survives body re-evaluation appState in the App; graphEntity, showSettings, newServerName in views
.environment(_:) Injects a value for the whole subtree PipelineVolumeView().environment(appState)
@Environment Reads a value an ancestor injected — by type, or by key path for built-ins @Environment(AppState.self), @Environment(\.dismiss), @Environment(\.openWindow)
Injection (Teraslice3DApp.swift) and retrieval (ControlOrnamentView.swift)—
// Owner — created once, lives as long as the app
@State private var appState = AppState()

WindowGroup {
    PipelineVolumeView()
        .environment(appState)          // put it in the environment
}

// Consumer — anywhere below, no constructor plumbing
struct ControlOrnamentView: View {
    @Environment(AppState.self) private var appState
    @Environment(\.openWindow) private var openWindow
}
⚠️
Ornaments and sheets need re-injection

PipelineVolumeView writes .ornament(…) { ControlOrnamentView().environment(appState) } — passing the state again explicitly. Ornaments, sheets and other presentations may be hosted outside the presenting view's environment chain, so re-injecting is the safe habit. Note that SettingsView and JobsInspectorView read @Environment(AppState.self) but are presented by .sheet { SettingsView() } without re-injection — a crash risk worth checking on device, since a missing environment value of this kind traps at runtime.

Bindable: read-write access to an observable

Sources/Views/ControlOrnamentView.swiftlines 38, 47
TextField("Search nodes or jobs...", text: Bindable(appState).searchText)

Picker("Filter Mode", selection: Bindable(appState).filterMode) { … }

A TextField needs a Binding<String> — a two-way handle, not a value. Bindable manufactures bindings to an @Observable object's properties. The more common spelling declares it once as a property, then uses $:

Idiomatic equivalent—
@Environment(AppState.self) private var appState

var body: some View {
    @Bindable var state = appState        // or a stored @Bindable property
    TextField("Search…", text: $state.searchText)
}

Both compile; Bindable(appState).searchText just constructs the wrapper inline each time. Compare with $showSettings in the same file — $ on a @State property is the same idea for view-local storage.

The refresh pipeline

Sources/App/AppState.swiftlines 35–99 (condensed)
public init() {
    Task { @MainActor in
        await refreshData()
        startAutoRefreshTask()
    }
}

@MainActor
public func refreshData() async {
    isRefreshing = true
    defer { isRefreshing = false }

    let graphResult = await apiClient.fetchPipelineGraph(serverConfig: activeServer)
    switch graphResult {
    case .success(let graph): self.graphData = graph
    case .failure:            self.graphData = MockGraphProvider.samplePipelineGraph()
    }

    let jobsResult = await apiClient.fetchJobs(serverConfig: activeServer)
    // … same shape …

    self.serverVersion = await apiClient.fetchVersion(serverConfig: activeServer)
    self.lastRefreshedAt = Date()
}

private func startAutoRefreshTask() {
    refreshTask?.cancel()
    refreshTask = Task { [weak self] in
        while !Task.isCancelled {
            try? await Task.sleep(nanoseconds: UInt64((self?.autoRefreshInterval ?? 30.0) * 1_000_000_000))
            if Task.isCancelled { break }
            if self?.isAutoRefreshEnabled == true { await self?.refreshData() }
        }
    }
}

deinit { refreshTask?.cancel() }

What each concurrency construct is doing

  • Task { … } — starts unstructured async work from a synchronous context. It runs concurrently with the caller and is not awaited, so init returns immediately while the fetch continues.
  • Task { @MainActor in … } — the closure runs on the main actor. Needed because everything it touches is main-actor-isolated.
  • @MainActor func refreshData() — the main actor is a global actor representing the main thread. All UI and all RealityKit entity mutation must happen here. Marking the method (rather than sprinkling DispatchQueue.main.async) is the modern way.
  • Cooperative cancellation — Task.isCancelled is polled; Task.sleep also throws on cancellation, which is what the try? swallows. Nothing is pre-empted: cancellation in Swift is always a request the task must honour.
  • await apiClient.… — apiClient is an actor, so each call hops to the client's isolation, runs there, and returns. The actor guarantees its own state is never touched concurrently.
🟠
Swift note · sleeping the modern way

Task.sleep(nanoseconds:) works, but the current API is Task.sleep(for: .seconds(30)), which takes a Duration and avoids the manual * 1_000_000_000. For a repeating timer that stays aligned to a schedule, AsyncTimerSequence from swift-async-algorithms, or a for await _ in … loop over an AsyncSequence, reads better than while + sleep.

End-to-end: one refresh

  timer fires (30 s)          user taps ⟳ in the ornament
         │                              │
         └──────────────┬───────────────┘
                        ▼
             AppState.refreshData()  @MainActor
                        │  await
                        ▼
          TerasliceAPIClient  (actor, off the main thread)
             URLSession ──► /api/pipeline_graph ──► JSONDecoder
                        │  Result<PipelineGraph, APIError>
                        ▼
             appState.graphData = graph        ← observation records a write
                        │
                        ▼
   SwiftUI invalidates views that read graphData
                        │
                        ▼
    PipelineVolumeView .onChange(of: appState.graphData)
                        │
                        ▼
      PipelineGraphEntity.updateGraph()  → simulation → projection → meshes

Note the hop pattern: main actor → actor → main actor. The values crossing that boundary (ServerConfig in, PipelineGraph out) are all Sendable structs, which is what makes the compiler accept it.

Swift 6 strict concurrency, and the escape hatch used here

Both the Xcode target (SWIFT_VERSION = 6.0) and the package (swift-tools-version: 6.0) opt into Swift 6 language mode, where data-race safety is a compile-time error rather than a warning. Two declarations in this codebase sidestep it:

AppState.swift line 13 · ForceSimulation3D.swift line 20—
public final class AppState: @unchecked Sendable { … }
public final class ForceSimulation3D: @unchecked Sendable { … }

Sendable means "safe to pass between concurrency domains". A mutable class is not Sendable, so the compiler would reject passing AppState into a Task. @unchecked disables the check without providing the safety — it is a promise you are making, and here nothing enforces it.

🔴
Gap · @unchecked Sendable is papering over the design

The honest annotation for AppState is @MainActor @Observable final class AppState. That makes it implicitly Sendable, removes the need for the per-method @MainActor attributes, and lets the compiler prove the UI state is only touched on the main thread. ForceSimulation3D is mutated only from @MainActor methods on PipelineGraphEntity, so the same applies — or make it a proper actor if you later want layout to run off the main thread (see chapter 06, where the 120-iteration solve currently blocks the main thread).

🔴
Gap · two entry points to the same startup work

init() already fires refreshData() and starts the auto-refresh loop. start() does the same thing again and is called from .task { appState.start() } in the non-visionOS branch of PipelineVolumeView. On macOS both run, so the first fetch happens twice. startAutoRefreshTask() cancels any previous task, so you don't get two timers — but doing work in init is worth avoiding on principle. The SwiftUI-native place for startup work is .task { }, which also cancels automatically when the view disappears.

Unused state worth knowing about

Four properties are declared, populated by the UI, and read by nothing: selectedNodeID, selectedLinkID, searchText (bound to the search field), and filterMode (bound to the picker). matchesSearch(_:) at the bottom of the file is the intended helper and is never called:

Sources/App/AppState.swiftlines 105–108
public func matchesSearch(_ text: String) -> Bool {
    guard !searchText.trimmingCharacters(in: .whitespacesAndNewlines).isEmpty else { return true }
    return text.localizedCaseInsensitiveContains(searchText)
}

So typing in the search box changes state and re-runs bodies, but no geometry responds. Chapter 10 sketches how to wire it into the RealityKit layer.
