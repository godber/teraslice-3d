Chapter 06 · simd & the layout engine

Layout math & simd

ForceSimulation3D is a from-scratch port of d3-force-3d in 172 lines of Swift: Coulomb repulsion, Hooke springs, centring gravity, velocity damping, and simulated annealing. It runs in abstract unitless space; a separate projection step turns that into metres.

simd SIMD3<Float> force-directed layout Fibonacci sphere annealing bounding-box projection

Two coordinate spaces, and why

The single most important architectural idea in the 3D half of this app: 

  Simulation space (ℝ³, unitless)            Volumetric space (metres, RealityKit)
  ────────────────────────────────           ─────────────────────────────────────
  seed radius        2.0                     volume            1.0 × 1.0 × 1.0 m
  ideal link length  1.5                     graph span        0.40 m  (targetVolumeSpan)
  repulsion          50.0                    node radius       0.008 – 0.035 m
  extent             grows with node count   link radius       0.002 – 0.015 m
                          │
                          └── VolumetricProjection:  p' = (p − centroid) · S
                                                     S = 0.40 / maxExtent

Physics constants that produce a pleasing layout have nothing to do with how big the result should look on your desk. Keeping them apart means the simulation can be tuned for topology while the projection guarantees the graph always fits the volume — a nine-node graph and a ninety-node graph both end up 40 cm across, just at different densities. The web frontend has the same split implicitly (unitless d3 coordinates, then a camera that frames them); in a volume there is no camera to move, so the scaling has to be explicit.

The simd vocabulary

simd is Apple's small-vector maths library, mapping onto SIMD CPU instructions. SIMD3<Float> is three floats in one register — the same type RealityKit uses for positions, so no conversion is ever needed.

Used hereMeaning
SIMD3<Float>(x, y, z), .zero, SIMD3(repeating:)Construction. .zero is the idiom you'll see most.
a + b, a - b, a * scalar, +=Component-wise operators, no loops.
simd_length(v)Euclidean magnitude — distance when applied to a delta.
simd_normalize(v)Unit vector. Undefined for a zero vector — hence the guards in this file.
simd_clamp(v, lo, hi)Component-wise clamp; also works on scalars.
simd_min / simd_maxComponent-wise, used to accumulate a bounding box.
simd_dot / simd_crossAngle and perpendicular axis — used for link orientation in chapter 07.
simd_quatf(angle:axis:)Quaternion rotation, also chapter 07.
v.x, v.y, v.zLane access; v[0] works too.
🟠
Swift note · Float, not Double

All the 3D maths is single-precision. That's not laziness: RealityKit, Metal and the GPU are Float throughout, and Swift will not implicitly convert between numeric types — mixing in a Double means writing Float(x) conversions everywhere. Note the explicit annotations in this file (let radius: Float = 2.0) which exist precisely to stop literals defaulting to Double.

The particle

Sources/Services/ForceSimulation3D.swiftlines 5–17
public struct Node3D: Identifiable, Sendable {
    public let id: String
    public var position: SIMD3<Float>
    public var velocity: SIMD3<Float>
    public var force: SIMD3<Float>

    public init(id: String, position: SIMD3<Float> = .zero) {
        self.id = id
        self.position = position
        self.velocity = .zero
        self.force = .zero
    }
}

Classic Verlet-style bookkeeping: accumulate force this tick, integrate into velocity, integrate that into position. Nodes live in a [String: Node3D] keyed by the graph node id, so the simulation can be reconciled against a new topology by id.

Seeding: the Fibonacci sphere

Sources/Services/ForceSimulation3D.swiftlines 39–56
let count = Float(graph.nodes.count)
for (index, node) in graph.nodes.enumerated() {
    if let existingNode = previousNodes[node.id] {
        // Topology reconciliation: preserve position, reset velocity
        nodes[node.id] = Node3D(id: node.id, position: existingNode.position)
    } else {
        // Fibonacci sphere distribution for uniform initial 3D spacing
        let phi = acos(1.0 - 2.0 * (Float(index) + 0.5) / max(count, 1.0))
        let theta = Float.pi * (1.0 + sqrt(5.0)) * Float(index)
        let radius: Float = 2.0

        let x = radius * sin(phi) * cos(theta)
        let y = radius * sin(phi) * sin(theta)
        let z = radius * cos(phi)

        nodes[node.id] = Node3D(id: node.id, position: SIMD3<Float>(x, y, z))
    }
}

Random initial positions make a force layout converge slowly and non-deterministically. A Fibonacci sphere (also called a spherical Fibonacci lattice) spreads N points near-uniformly over a sphere: phi walks the polar angle so equal-area bands get equal point counts, and theta advances by the golden angle π(1 + √5) each step so successive points never line up. The result is deterministic, evenly spaced, and gives the solver a good starting guess.

Reconciliation — why the graph doesn't jump every 30 seconds

setup(graph:) is called on every refresh. Nodes that already exist keep their positions and have their velocity zeroed; only genuinely new nodes get seeded. This mirrors reconcileGraphData in the web frontend and is what makes a 30-second poll feel like a live view rather than a reshuffle. The behaviour is pinned by a test (testForceSimulationReconciliationPreservesPositions).

One consequence worth knowing: a node that disappears from the topology is dropped entirely, and if it comes back it is re-seeded from scratch at whatever index it now occupies.

One tick of the solver

Sources/Services/ForceSimulation3D.swiftlines 60–135 (condensed)
public func tick(alpha: Float = 1.0) {
    let keys = Array(nodes.keys)

    // 1. Reset forces
    for key in keys { nodes[key]?.force = .zero }

    // 2. Coulomb node repulsion — every pair, O(n²)
    for i in 0..<keys.count {
        for j in (i + 1)..<keys.count {
            var delta = nodeA.position - nodeB.position
            var dist  = simd_length(delta)
            if dist < 0.001 {                       // coincident: jitter apart
                delta = SIMD3<Float>(Float.random(in: -0.01...0.01), …)
                dist  = simd_length(delta)
            }
            let distSq = max(0.01, dist * dist)     // avoid divide-by-zero blowup
            let forceMagnitude = (repulsionStrength / distSq) * alpha
            let forceVec = simd_normalize(delta) * forceMagnitude
            nodes[idA]?.force += forceVec
            nodes[idB]?.force -= forceVec           // equal and opposite
        }
    }

    // 3. Hooke link attraction — springs pull toward idealLinkLength
    for link in links {
        let delta = nodeTarget.position - nodeSource.position
        let dist  = simd_length(delta)
        guard dist > 0.0001 else { continue }
        let displacement   = dist - idealLinkLength
        let forceMagnitude = springStrength * displacement * alpha
        let forceVec       = simd_normalize(delta) * forceMagnitude
        nodes[link.source]?.force += forceVec
        nodes[link.target]?.force -= forceVec
    }

    // 4. Gravity toward the origin, proportional to distance
    for key in keys {
        let dist = simd_length(node.position)
        if dist > 0.001 {
            nodes[key]?.force += -simd_normalize(node.position) * (gravityStrength * dist) * alpha
        }
    }

    // 5. Integrate
    for key in keys {
        node.velocity = (node.velocity + node.force) * damping
        node.position += node.velocity
        if let bounds = boundsHalfWidth {           // nil in production
            node.position.x = simd_clamp(node.position.x, -bounds, bounds)
            node.position.y = simd_clamp(node.position.y, -bounds, bounds)
            node.position.z = simd_clamp(node.position.z, -bounds, bounds)
        }
        nodes[key] = node
    }
}

The four forces

  • Repulsion — inverse-square, like charged particles: F = k / d². Pushes unconnected nodes apart so the graph spreads out. This is the term that costs O(n²).
  • Springs — linear in displacement from idealLinkLength: F = k(d − L). Pulls connected nodes to a comfortable distance; pushes them apart if too close. Note the sign convention — the force is applied toward the target on the source and vice versa, so an over-long link contracts.
  • Gravity — toward the origin, proportional to distance, which keeps disconnected components from drifting off to infinity. In a bounded volume that matters more than on an infinite web canvas.
  • Damping — velocity is multiplied by 0.85 every tick, bleeding energy so the system settles instead of oscillating.

Annealing

Sources/Services/ForceSimulation3D.swiftlines 166–171
public func runSimulation(iterations: Int = 120) {
    for i in 0..<iterations {
        let alpha = max(0.01, 1.0 - (Float(i) / Float(iterations)))
        tick(alpha: alpha)
    }
}

alpha ramps from 1.0 down to 0.01, scaling all three forces. Big moves early to escape bad configurations, tiny moves late to settle — the same cooling schedule d3-force uses. 120 iterations is a fixed budget rather than a convergence test.

TunableValueRaise it to…
repulsionStrength50.0spread nodes further apart

🧮
Clamping to a cube is not the same as fitting a sphere

When boundsHalfWidth is set, each axis is clamped independently, so nodes pile up flat against the faces of a cube. That's why the production path leaves it nil and rescales afterwards instead — clamping distorts the layout, scaling preserves it. The test testForceSimulationBounds exists to verify the clamp still works if you turn it on.

Projection: unitless → metres

Sources/RealityKit/PipelineGraphEntity.swiftlines 6–37 (condensed)
public struct VolumetricProjection {
    public let centroid: SIMD3<Float>
    public let scale: Float
    public let targetVolumeSpan: Float

    public init(nodes: [Node3D], targetVolumeSpan: Float = 0.40) {
        var minPos = SIMD3<Float>(repeating: Float.greatestFiniteMagnitude)
        var maxPos = SIMD3<Float>(repeating: -Float.greatestFiniteMagnitude)
        for node in nodes {
            minPos = simd_min(minPos, node.position)
            maxPos = simd_max(maxPos, node.position)
        }

        self.centroid = (minPos + maxPos) * 0.5
        let extent    = maxPos - minPos
        let maxExtent = max(extent.x, max(extent.y, extent.z))
        self.scale    = targetVolumeSpan / max(maxExtent, 0.001)
    }

    public func project(_ position: SIMD3<Float>) -> SIMD3<Float> {
        (position - centroid) * scale
    }
}

A bounding-box fit, in three moves: accumulate min/max, take the box centre as the centroid, and scale by 0.40 / longest axis. Because the same factor applies to all three axes the shape is never distorted, and because the centroid is subtracted the graph is always centred on the volume's origin. max(maxExtent, 0.001) guards the single-node case where every extent is zero.

A subtlety: the fit is computed from node centres, so a sphere's radius can push geometry slightly past ±0.20 m. With a 1 m volume and node radii capped at 3.5 cm there's plenty of slack — the test suite asserts the projected span stays inside ±0.35 m for a 0.70 m target.

🔴
Gap · two implementations of the same fit

ForceSimulation3D.fitToVolume(targetHalfWidth:) does exactly what VolumetricProjection does, but destructively rewrites the simulation's own coordinates. Nothing in the render path calls it — only testForceSimulationFitToVolume. Keeping both is a live trap: calling fitToVolume would bake metres into the "unitless" space and the projection would then scale it a second time. The projection version is the one to keep; fitToVolume and its test are the ones to delete.

Performance, honestly

  • O(n²) per tick × 120 ticks. For the 9-node fixture that's ~4,300 pair computations total — nothing. At 100 nodes it's ~594,000; at 500 nodes ~15 million, and each inner step also does two dictionary lookups and a copy-on-write. The backend caps job queries at 500, so a large cluster is a realistic worry.
  • It runs synchronously on the main actor. updateGraph() is @MainActor and calls runSimulation(iterations: 120) inline, so the whole solve happens between two frames of a 90 Hz display. On visionOS a dropped frame is felt more than on a screen — the world visibly stutters. Moving the solve to a background Task (or making ForceSimulation3D an actor) and only touching entities on the main actor is the clean fix; see chapter 10.
  • Cheap structural wins: iterate a contiguous [Node3D] array with an index-based id map instead of mutating through a dictionary; hoist nodes[key] reads out of the inner loop; skip the repulsion pair loop entirely beyond a distance cutoff. The textbook answer is a Barnes–Hut octree (O(n log n)), which is what d3-force-3d uses under the hood.
  • Float.random in the hot path only fires for coincident nodes, but it does make the simulation non-deterministic in that case. Fine here; worth knowing if you ever want reproducible layouts for screenshots or tests.
