Chapter 09 · Toolchain

Build & test

The project has two build systems on purpose: SwiftPM for fast, headless logic tests on your Mac, and an Xcode project for the actual visionOS app. Here's how to drive both, what the nine tests cover, and what isn't tested at all.

swift test xcodebuild visionOS Simulator XCTest Swift Testing

⚠️
Adding a file means touching both

SwiftPM picks up new files under Sources/ automatically; the Xcode project does not — each file is listed individually in project.pbxproj. A new file added outside Xcode will compile under swift build and be silently missing from the app, producing confusing "cannot find X in scope" errors only in the visionOS build. Add files through Xcode, or remember to update both.

Running it

Logic tests, no simulator (seconds)

Terminal—
cd Teraslice3D-visionOS
swift build          # builds the macOS slice
swift test           # runs the 9 XCTest cases

Verified with the toolchain in this repo (Xcode 26.6, Swift 6.3.3): all nine tests pass in about 0.03 s. This is the fast feedback loop for anything in Models/ or Services/.

The app, in the simulator

The straightforward path is Xcode: open Teraslice3D.xcodeproj, pick an Apple Vision Pro simulator destination, press ⌘R. From the command line:

Terminal—
# what destinations exist for this scheme
xcodebuild -project Teraslice3D.xcodeproj -scheme Teraslice3D -showdestinations

# build for the simulator
xcodebuild -project Teraslice3D.xcodeproj -scheme Teraslice3D \
           -destination 'platform=visionOS Simulator,name=Apple Vision Pro' build

# which visionOS SDKs are installed
xcodebuild -showsdks | grep -i visionos

The visionOS platform support (SDK + simulator runtime) is a separate download in Xcode → Settings → Components; without it, -showdestinations lists only placeholders and the build fails.

With the backend attached

Terminal — from the repo root—
cd backend
TERASLICE_URL="http://your-teraslice:5678" uv run python -m fastapi dev
# serves http://127.0.0.1:8000 — the app's ServerConfig.defaultLocal

In the simulator, 127.0.0.1 is the host Mac, so this works unchanged. On a real Vision Pro, use the Mac's LAN address via Settings → Add Custom Server in the app, and bind the backend to 0.0.0.0. Running on device also requires enabling Developer Mode on the headset and a signing team on the target. If nothing is listening, the app shows mock data rather than an error — see the warning in chapter 05.

Navigating the simulator

  • Look-and-click is simulated with the mouse; hold option and drag to move the "hands"/pinch, and use the arrow keys or WASD-style controls in the simulator's control bar to move your viewpoint around the scene.
  • Because you can move the camera, the simulator is the fastest way to check that the graph is actually 3D and centred — it's easy to build something that looks fine head-on and is a flat plane from the side.
  • The simulator does not reproduce real-world lighting or passthrough, so materials and contrast should be sanity-checked on device before you trust them.

What the nine tests cover

TestAsserts
testMockGraphProviderDataFixture is non-empty and at least one node is classified as incoming Kafka.
testAPIClientMockFallbackfetchPipelineGraph with isMock returns a populated graph without touching the network.
testJobDetailsStatusParsingThe nested ex._status decoder produces .running from a literal JSON string.
testForceSimulationSetupAndTicksNode/link counts populate, and no coordinate is NaN after 120 iterations. The single most valuable test here — NaN is the classic force-layout failure.
testForceSimulationBoundsWith boundsHalfWidth = 0.40, all coordinates stay clamped.
testForceSimulationFitToVolumefitToVolume centres at the origin and respects the half-width. (Tests a method the app never calls — ch. 06.)
testVolumetricProjectionCenteringAndScalingProjected positions are centred and fit ±0.35 m for a 0.70 m target span.
testForceSimulationReconciliationPreservesPositionsRe-running setup keeps existing positions and zeroes velocity.
testAdaptiveGeometryScalingMore workers → thicker pipe, and both ends stay inside the 2–15 mm clamp.

All nine use XCTest: a final class … : XCTestCase, methods prefixed test, and XCTAssert* functions with a trailing message. Two Swift details worth noting: @testable import Teraslice3D gives the test target access to internal symbols, and func testAPIClientMockFallback() async shows that XCTest methods can be async — no expectations or callbacks needed for actor calls.

🧪
XCTest vs Swift Testing

Apple's current test framework is Swift Testing — @Test functions, #expect(…) macros, parameterised cases, and plain structs instead of XCTestCase subclasses. It ships with the toolchain and coexists with XCTest in the same target (the swift test output above shows both runners starting; the Swift Testing one finds zero tests). Nothing here needs migrating, but new tests are nicer to write in it: 

import Testing

@Test("worker count scales pipe radius")
func pipeRadius() {
    #expect(radius(forWorkers: 200) > radius(forWorkers: 1))
}

What isn't tested

  • The HTTP paths. Only the isMock short-circuit is exercised; status-code handling, decode failures, and the fallback-to-mock behaviour never run. The urlSession injection point exists for exactly this — a URLProtocol stub would cover all four endpoints without a server.
  • Anything RealityKit. No test constructs a NodeEntity or LinkEntity. Notably, testAdaptiveGeometryScaling re-implements the worker-scaling formula in the test body rather than calling into LinkEntity, so the two copies can drift apart and the test would still pass. Extracting the formula into a plain, platform-independent function would make it genuinely covered.
  • The views. No snapshot or UI tests; SwiftUI previews aren't used either, and they'd be the cheapest win here (#Preview works for the ornament, list and form).
  • CI. .github/workflows/test.yml runs the Python backend tests and a Docker build on ubuntu-latest; nothing builds or tests the Swift. Adding swift test requires a macOS runner, and a full xcodebuild for visionOS requires one with the visionOS SDK installed.
🔍
Debugging tools worth knowing

When geometry is missing or misplaced, the useful tools are Xcode's RealityKit debugger (capture the running scene and inspect the entity hierarchy, transforms and components live), Instruments with the RealityKit templates for frame timing, and simply logging entity.position — a NaN transform silently removes an entity from the render, which is the single most common "nothing appears" cause in code like LinkEntity.
