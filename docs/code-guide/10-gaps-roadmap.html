Chapter 10 · What's missing, and what it needs

Gaps & roadmap

Everything the code stages but doesn't finish, each paired with the specific SDK pieces that would complete it. Ordered roughly by learning value per hour: the first three teach you the most about visionOS, the rest are ordinary software work.

🗺️
Where this comes from

AVP-SPEC.md in the repo root defines four "chunks" and marks 1 done, 2 and 3 in progress, 4 pending. This chapter reads the code instead of the plan: the difference between what's written and what actually runs. Nothing here is a criticism of a work-in-progress branch — it's a map of where to put your hands next.

1 · Make things tappable

Highest value per line of code in the whole project. The entities already have CollisionComponent + InputTargetComponent; the missing half is a SwiftUI gesture on the RealityView, and a place to put the result — which AppState.selectedNodeID / selectedLinkID already are.

Sketch — PipelineVolumeView.swift—
RealityView { content in … }
    .gesture(
        SpatialTapGesture()
            .targetedToAnyEntity()
            .onEnded { value in
                switch value.entity {
                case let node as NodeEntity: appState.selectedNodeID = node.nodeID
                case let link as LinkEntity: appState.selectedLinkID = link.linkID
                default: break
                }
            }
    )

Note how the NodeEntity/LinkEntity subclasses pay off here: the as? cast recovers the domain identity directly from the hit entity. The same .targetedToAnyEntity() pattern extends to DragGesture (move a node) and RotateGesture3D (spin the whole graph — the purpose of that unused Rotation3D state).

  • docsSpatialTapGesture · EntityTargetValue · RotateGesture3D
  • articleTransforming RealityKit entities with gestures
  • videoWWDC23: Design for spatial input

2 · Labels and info cards (attachments)

Right now the volume shows unlabelled coloured balls: you cannot tell which topic is which without the web UI open beside you. Two levels of fix:

  • Cheap: TextComponent or MeshResource.generateText child entities, plus BillboardComponent so they turn to face you as you move.
  • Right: attachments — real SwiftUI views placed in 3D space. You declare them in the RealityView's attachments: builder (or attach a ViewAttachmentComponent), then position the resulting entity beside the selected node. That gets you the glassmorphic detail card from the spec — job name, worker count, status pill, and buttons that open Teraslice or Grafana — with all the SwiftUI you already know.

Opening those URLs is one environment value: @Environment(\.openURL) private var openURL, then openURL(url) — the decoded link.url and link.grafana_url are sitting unused in the model.

Needs
  • docsRealityView(make:update:attachments:) · ViewAttachmentComponent
  • docsTextComponent · BillboardComponent · openURL
  • videoWWDC25: Better together — SwiftUI and RealityKit

3 · A frame loop, so the graph moves

PipelineGraphEntity.stepSimulation() is written and orphaned (chapter 07). Wiring it up turns a static snapshot into a graph that visibly settles, which is most of why force-directed layouts are compelling. Two idiomatic routes:

Option A — subscribe to scene updates—
RealityView { content in
    content.add(graphEntity)
    _ = content.subscribe(to: SceneEvents.Update.self) { _ in
        graphEntity.stepSimulation()
    }
}

Option B is a real RealityKit System: register a System that runs each frame over entities carrying a component you define. More ceremony, but it's the ECS-native design, composes with other systems, and keeps the frame work out of your view layer. Either way, hold the subscription (a Cancellable) somewhere it won't be deallocated, and keep the per-frame cost bounded — see the O(n²) discussion in chapter 06.

4 · Make search and filter do something

searchText, filterMode and matchesSearch(_:) exist; nothing consumes them. The visionOS-appropriate implementation for the two modes:

  • Highlight: keep everything, and dim non-matches with OpacityComponent (opacity = 0.15). Cheap, reversible, and preserves the shape of the graph — much better in 3D than removing things, because a hole in a graph is disorienting.
  • Remove unmatched: removeFromParent() on non-matching entities, or set opacity = 0 plus removing the collider so they can't be tapped.
  • Drive both from a .onChange(of: appState.searchText) on the RealityView, calling a new graphEntity.applyFilter(matching:mode:). No relayout needed — filtering should never move nodes, or the user loses their mental map.
  • Consider replacing the hand-built capsule search field with .searchable for the system look and keyboard behaviour.

5 · Tell the truth about failures

The most important non-3D fix, and the one with real operational consequences for a monitoring tool (chapter 05): every failure currently lands on the same fixture data. Concretely:

  1. Stop returning .success(mock) from catch blocks in TerasliceAPIClient; return .failure(.networkError(error)) / .failure(.decodingError(error)) — the two enum cases that are currently never constructed.
  2. In AppState.refreshData(), on failure keep the previous graphData and set a new lastError: String? plus a connectionState enum.
  3. Show it: a red/amber dot in the ornament next to the server name, and the lastRefreshedAt timestamp that is already tracked and never displayed.
  4. Replace print with Logger so device logs are usable.

6 · Move the solve off the main actor

runSimulation(iterations: 120) runs synchronously inside a @MainActor method. At the fixture's nine nodes it's invisible; on a real cluster with hundreds of connectors it will drop frames, and dropped frames on a head-mounted display are unpleasant in a way they aren't on a monitor. The shape of the fix:

  • Make ForceSimulation3D an actor (dropping @unchecked Sendable), or run the solve in Task.detached and return a plain [String: SIMD3<Float>].
  • await the result on the main actor and apply it to entities there — entity mutation must stay main-actor.
  • Then reduce the cost: distance cutoff or Barnes–Hut for repulsion, arrays instead of dictionary mutation, and incremental relayout when only a few nodes changed.

7 · Present the jobs inspector

JobsInspectorView is complete and unreachable; showInspector in the ornament is declared and unused. Two designs, and the spatial one is better:

  • Quick: a .sheet(isPresented: $showInspector) { JobsInspectorView() } mirroring the settings button — remembering to inject .environment(appState).
  • Better: a separate WindowGroup(id: "jobs-inspector") opened with openWindow(id:), so the list floats beside the volume instead of covering it. This is the visionOS advantage over a browser tab, and it's also what finally makes use of the unused openWindow already declared in ControlOrnamentView. Selecting a row could then set selectedNodeID and pulse the corresponding entity.

8 · The immersive space

The spec's headline idea — walk inside a pipeline — is untouched. It's a scene type plus a projection change, not a rewrite:

Sketch — Teraslice3DApp.swift—
ImmersiveSpace(id: "pipeline-immersive") {
    PipelineImmersiveView()
        .environment(appState)
}
.immersionStyle(selection: $immersionStyle, in: .mixed, .progressive, .full)
  • Open it with @Environment(\.openImmersiveSpace) (it's async: await openImmersiveSpace(id:)), close with dismissImmersiveSpace.
  • VolumetricProjection is already the seam for this: pass a much larger targetVolumeSpan (say 4–6 m) and the same code fills a room instead of a box.
  • Node and pipe radii, and the 0.008–0.035 m clamps, all need a second set of constants at room scale.
  • Ornaments don't apply in an immersive space — controls become in-world attachments or stay in a separate window.
Needs
  • docsImmersiveSpace · openImmersiveSpace · Creating fully immersive experiences
  • videoWWDC24: Dive deep into volumes and immersive spaces · Develop your first immersive app

🎯
If you only do three things

Add the tap gesture (§1) — it teaches you the visionOS input model and immediately makes the app feel alive. Add attachments (§2) — labels are what make the visualisation legible, and it's the piece with no web equivalent. Make failures visible (§5) — because a monitoring tool that shows plausible fake data when it can't reach the cluster is worse than one that shows nothing.
